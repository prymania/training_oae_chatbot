1.1

แนวคิดการทำงาน: RAG คืออะไร

ปัญหาของแชทบอท AI ทั่วไป (เช่น ChatGPT แบบเปล่า ๆ) คือมันตอบจาก "ความจำ" ที่เรียนรู้มาตอนฝึกโมเดล ซึ่งอาจไม่มีข้อมูลล่าสุด ไม่มีข้อมูลเฉพาะของหน่วยงาน และที่อันตรายที่สุดคือ สามารถ "มั่ว" ตัวเลขหรือข้อเท็จจริงขึ้นมาเองได้ (เรียกว่า hallucination) — ซึ่งยอมรับไม่ได้สำหรับข้อมูลราชการที่ต้องอ้างอิงได้

RAG (Retrieval-Augmented Generation) แก้ปัญหานี้ด้วยการ "บังคับ" ให้ AI ตอบจากเอกสารจริงเท่านั้น โดยแบ่งการทำงานเป็น 2 ขั้นเสมอ:

  1. Retrieval (ค้นหา) — เมื่อผู้ใช้ถามคำถาม ระบบจะค้นหาย่อหน้า/ส่วนของเอกสารที่เกี่ยวข้องที่สุดจากคลังเอกสารที่นำเข้าไว้ล่วงหน้า
  2. Generation (สร้างคำตอบ) — ส่งย่อหน้าที่ค้นเจอ (เรียกว่า "context") ให้โมเดลภาษา (LLM) อ่าน แล้วให้เรียบเรียงเป็นคำตอบภาษาธรรมชาติ พร้อมอ้างอิงแหล่งที่มา

ผลลัพธ์คือคำตอบที่ ตรวจสอบย้อนกลับได้ — ทุกคำตอบสามารถอ้างอิงกลับไปยังเอกสารต้นฉบับ ข้อ [1] [2] [3] ที่ระบบใช้ประกอบคำตอบ และถ้าไม่มีข้อมูลในเอกสาร ระบบจะบอกตรง ๆ ว่าไม่มีข้อมูล แทนที่จะเดา

1.2

สถาปัตยกรรมระบบโดยรวม

ระบบประกอบด้วย 5 ส่วนหลักที่ทำงานร่วมกัน — ผู้ใช้ไม่เห็นความซับซ้อนนี้ เห็นแค่หน้าแชท

หลักการออกแบบสำคัญ: ทุกส่วนเป็นบริการแยกกัน (loosely coupled) — ถ้า DeepSeek ล่ม ระบบยังค้นเอกสารได้ ถ้า API ภายนอกล่ม ระบบยัง fallback กลับไปตอบจากเอกสารอย่างเดียวได้ ไม่มีจุดใดจุดหนึ่งทำให้ทั้งระบบหยุดทำงาน (ยกเว้นฐานข้อมูลและ backend เอง)

Ollama (bge-m3) — แปลงข้อความเป็นเวกเตอร์

ใช้ 2 จังหวะ: ตอนนำเข้าเอกสาร (แปลงทุกชิ้นเอกสาร) และตอนตอบคำถาม (แปลงคำถามของผู้ใช้)

คอมพิวเตอร์ค้นหา "ความหมาย" ของข้อความโดยตรงไม่ได้ — bge-m3 จึงแปลงข้อความ (ไม่ว่าจะเป็นชิ้นเอกสารหรือคำถามของผู้ใช้) ให้เป็นชุดตัวเลข 1024 ตัวที่เรียกว่า เวกเตอร์ ข้อความที่ความหมายใกล้เคียงกันจะได้เวกเตอร์ที่ "อยู่ใกล้กัน" ในทางคณิตศาสตร์ ทำให้เปรียบเทียบความคล้ายกันได้

1.4

ขั้นตอนการทำงานเมื่อผู้ใช้ถามคำถาม

นี่คือหัวใจของระบบ (app/services/rag.py, app/routers/chat.py) — คำถาม 1 ข้อ ผ่านกี่ขั้นตอนกว่าจะกลายเป็นคำตอบ

รายละเอียดแต่ละขั้นตอน (ไฟล์อ้างอิง):

  1. คัดกรองเจตนา (Intent Router) — app/services/intent_router.py. คำถามประเภททักทาย ขอบคุณ ขอข้อมูลส่วนบุคคล หรือหลุดหัวข้อ จะถูกตอบด้วยข้อความสำเร็จรูปทันที ไม่ต้องเสียเวลาค้นเอกสารหรือเรียก LLM คำถามเชิงขอคำแนะนำยังค้นเอกสารได้แต่ระบบจะเลี่ยงการ "สั่งยา/สั่งวิธีรักษา" ตรง ๆ
  2. เลือกหมวดสินค้า (Domain Router) — app/services/domain_router.py. ทำงานเฉพาะเมื่อผู้ใช้เลือกหมวด "ทั้งหมด" — LLM จะวิเคราะห์คำถามแล้วเดาว่าควรค้นเฉพาะหมวดไหน (เช่น กุ้ง, โคนม) เพื่อความแม่นยำ ถ้าเดาไม่ได้ก็ค้นทั้งหมดตามเดิม (ไม่แย่ไปกว่าการไม่ทำเลย)
  3. ขยายคำค้นหา (Query Expansion) — expand_query() ใน rag.py. คำถาม 1 ข้อ อาจมีหลายแง่มุม LLM จะช่วยแตกออกเป็น 2-3 คำค้นหาย่อยที่ครอบคลุมมุมต่าง ๆ (เช่น "อาการของโรค" + "วิธีป้องกัน")
  4. ค้นหาเวกเตอร์ (Vector Retrieval) — คำค้นหาแต่ละคำถูกแปลงเป็นเวกเตอร์ด้วย bge-m3 แล้วค้นใน PostgreSQL/pgvector ด้วย cosine similarity (ความคล้ายเชิงมุม) หาย่อหน้าที่ใกล้เคียงที่สุด 10 อันดับต่อคำค้นหาย่อย ทำงานคู่ขนานทุกคำค้นหาย่อยพร้อมกันเพื่อความเร็ว
  5. คัดกรอง + จัดอันดับใหม่ (Rerank) — rerank_chunks(). ตัดย่อหน้าที่คะแนนต่ำกว่า 0.35 ทิ้ง แล้วให้คะแนนพิเศษกับเอกสารที่ ใหม่กว่า และมาจากหน่วยงานทางการ (สศก., กรมปศุสัตว์ ฯลฯ) เพื่อไม่ให้เอกสารเก่าที่ OCR ไว้แย่งที่เอกสารทางการฉบับล่าสุด
  6. เสริมข้อมูลสด (Tool Routing) — app/services/tool_router.py. ก่อนตอบ DeepSeek จะพิจารณาว่าคำถามต้องใช้ "ข้อมูลสด" หรือไม่ (ราคาสินค้าล่าสุด, พยากรณ์อากาศ, ระดับน้ำ, ศัตรูพืชระบาด ฯลฯ) แล้วเลือกเรียก API ภายนอกที่เกี่ยวข้องแบบคู่ขนาน ผลลัพธ์ถูกผสมเข้ากับบริบทก่อนส่งให้ LLM ตอบ — ถ้าเรียกไม่สำเร็จ ระบบ fallback กลับไปใช้กติกาคำสำคัญแบบเดิม ไม่กระทบการตอบ
  7. สร้างคำตอบ (Answer Generation) — DeepSeek อ่านคำถาม + ประวัติการสนทนา + บริบทที่ค้นได้ทั้งหมด แล้วเรียบเรียงคำตอบพร้อมอ้างอิงหมายเลข [1][2][3] ตอบแบบสตรีมทีละคำ (คล้าย ChatGPT พิมพ์ทีละตัวอักษร) ผ่าน Server-Sent Events
  8. บันทึกและงานเบื้องหลัง — คำถาม/คำตอบถูกบันทึกลง qa_logs เพื่อใช้วิเคราะห์ในแดชบอร์ดแอดมิน ส่วนคำถามแนะนำต่อยอด (follow-up chips) จะถูกสร้างแบบ background หลังตอบเสร็จแล้ว เพื่อไม่ให้ผู้ใช้ต้องรอ
หลักการสำคัญ

ถ้าระบบค้นไม่เจอเอกสารที่เกี่ยวข้องเลย (coverage = "none") ระบบจะไม่ปล่อยให้ DeepSeek ตอบแบบเดา แต่จะตอบข้อความสำเร็จรูปว่าไม่มีข้อมูลในเอกสารทันที — นี่คือกลไกป้องกัน hallucination ที่สำคัญที่สุดของระบบ

1.5

ขั้นตอนการนำเข้าข้อมูลเข้าคลังความรู้ (Ingestion)

ก่อนแชทบอทจะตอบอะไรได้ ต้อง "ป้อน" เอกสารเข้าระบบก่อน — สคริปต์หลักคือ scripts/batch_ingest.py

  1. เตรียมโฟลเดอร์ PDF ไว้ที่ pdf/<หมวดสินค้า>/ พร้อมไฟล์ index.json ที่ระบุ หมวดหมู่ ปี หน่วยงานเจ้าของเอกสาร และ URL ต้นฉบับ
  2. ระบบส่งแต่ละหน้า PDF ไปให้ Typhoon OCR อ่านตัวอักษรภาษาไทยออกมาเป็นข้อความ (ทำเป็นชุด ๆ เพื่อเลี่ยงโดนจำกัดอัตราการเรียก API)
  3. ข้อความที่ OCR ได้ถูกแคชไว้ที่ data/ocr_output/ — ถ้าต้องรันซ้ำ ระบบจะข้ามขั้นตอน OCR ได้ (ประหยัดเวลา/ค่าใช้จ่าย)
  4. ตัดข้อความเป็นชิ้นย่อย (chunk) ขนาด ~1,500 ตัวอักษร ทับซ้อนกัน 200 ตัวอักษร (กันบริบทขาดตรงรอยตัด)
  5. แต่ละชิ้นถูกแปลงเป็นเวกเตอร์ด้วย Ollama bge-m3 แล้วบันทึกลงตาราง knowledge_base

มีสคริปต์ย่อยสำหรับสถานการณ์ต่าง ๆ:

  • scripts/ingest_missing.py — นำเข้าเฉพาะ PDF ใหม่ที่ยังไม่มีในระบบ (ไม่ต้องรันใหม่ทั้งหมด)
  • scripts/reingest_from_ocr.py — สร้าง embedding ใหม่จากข้อความ OCR ที่แคชไว้แล้ว (เช่น ตอนปรับขนาด chunk ใหม่)
  • scripts/ingest_oae_sheet.py — ดึงเอกสารจำนวนมากจาก Google Sheet ของสำนักงานเศรษฐกิจการเกษตร (OAE) แบบสตรีม ทีละไฟล์ ทำงานต่อได้แม้หยุดกลางคัน
1.6

ระบบผู้ใช้งานและสิทธิ์การเข้าถึง

👤 ผู้ใช้ทั่วไป (Guest)

เข้าใช้แชทได้ทันทีไม่ต้องสมัคร ระบุตัวตนด้วย UUID ชั่วคราว บทสนทนาเก็บแบบ sliding window (10 ข้อความล่าสุด)

🔐 ผู้ใช้ลงทะเบียน

สมัครด้วยอีเมล + รหัส OTP 6 หลัก (ส่งผ่าน SMTP) เข้าสู่ระบบด้วยอีเมล/รหัสผ่าน ยืนยันตัวตนด้วย JWT (หมดอายุ 8 ชม.) ประวัติแชทถูกบันทึกถาวร

🛡️ ผู้ดูแลระบบ (Admin)

ล็อกอินแยกต่างหาก จัดการคลังความรู้ ดูสถิติ วิเคราะห์คำถามที่ตอบไม่ได้ จัดการหมวดหมู่สินค้า

💬 LINE

ผู้ใช้ LINE ถามผ่าน Rich Menu ได้เช่นกัน ระบบยืนยันด้วยลายเซ็น HMAC ของ LINE แล้วใช้ RAG pipeline เดียวกับหน้าเว็บ

รหัสผ่านทุกบัญชีถูกแฮชด้วย PBKDF2 (ไม่เก็บรหัสผ่านจริง) การพิสูจน์ตัวตน API ใช้ JWT มาตรฐาน (HS256) ปุ่มล็อกอินผ่าน Google/Facebook/LINE ถูกถอดออกแล้ว เหลือเฉพาะอีเมล/รหัสผ่านเพื่อความง่ายในการดูแล

1.7

ระบบเสริมรอบข้าง

นอกจากแชทหลัก ระบบยังมีชั้นข้อมูลและหน้าจอเพิ่มเติมที่สร้างมูลค่าให้หน่วยงาน:

  • API สาธารณะ (/api/v1) — ให้หน่วยงาน/นักพัฒนาภายนอกดึงข้อมูลราคาสินค้า สถิติ และผลตอบคำถามผ่าน API มาตรฐาน มีระบบกุญแจ API และจำกัดอัตราการเรียก
  • พอร์ทัลข้อมูล (/portal) — หน้าแสดงราคาสินค้าสด ความลึกของคลังความรู้ และลิงก์ต่อไปยังแชทโดยตรง
  • แดชบอร์ดผู้บริหาร (/dashboard) — สรุปตัวชี้วัดตามมิติการตัดสินใจ (การผลิต/ตลาด/ความเสี่ยง/การเงิน/ฟาร์ม) แนวโน้ม 30 วัน และช่องว่างของข้อมูล
  • แบบสำรวจความพึงพอใจ (/survey) — เก็บความคิดเห็นผู้ใช้ แยกอัตโนมัติว่ามาจากเว็บหรือ LINE
  • เว็บผลการทดสอบ (Benchmarks) — เว็บไซต์แยกที่สรุปผลทดสอบคุณภาพคำตอบ (150 คำถามต่อหมวดสินค้า) เผยแพร่ที่ OAE-chatbot-benchmarks.netlify.app
A

ภาคผนวก: คำศัพท์เทคนิคที่ควรรู้

RAG (Retrieval-Augmented Generation)
เทคนิคให้ AI ตอบโดยอ้างอิงเอกสารจริงที่ค้นเจอ แทนที่จะตอบจากความจำล้วน ๆ
Embedding (เวกเตอร์)
การแปลงข้อความเป็นชุดตัวเลขที่แทนความหมาย ข้อความที่ความหมายใกล้กันจะมีเวกเตอร์ใกล้กัน
Cosine similarity
วิธีวัดความคล้ายระหว่างเวกเตอร์สองชุดโดยดูมุมระหว่างกัน ใช้หาเอกสารที่เกี่ยวข้องกับคำถาม
pgvector
ส่วนขยายของ PostgreSQL ที่เพิ่มความสามารถเก็บและค้นหาเวกเตอร์ได้ในตัว
LLM (Large Language Model)
โมเดลภาษาขนาดใหญ่ที่เรียบเรียงข้อความได้เป็นธรรมชาติ (เช่น DeepSeek, GPT, Claude)
Token
หน่วยย่อยของข้อความที่ LLM ใช้นับความยาวและคิดค่าใช้จ่าย (โดยประมาณ 1 token ≈ คำ/พยางค์สั้น ๆ)
Chunk (ชิ้นเอกสาร)
ส่วนย่อยของเอกสารที่ตัดมาเก็บแยกเป็นแถวในฐานข้อมูล เพื่อให้ค้นหาและอ้างอิงเฉพาะจุดได้
OCR (Optical Character Recognition)
เทคโนโลยีอ่านตัวอักษรจากภาพ/เอกสารสแกน แปลงเป็นข้อความที่คอมพิวเตอร์ประมวลผลได้
JWT (JSON Web Token)
โทเคนยืนยันตัวตนที่เข้ารหัสข้อมูลผู้ใช้ไว้ในตัวเอง ไม่ต้องเช็คฐานข้อมูลทุกครั้งที่ยืนยันสิทธิ์
SSE (Server-Sent Events)
วิธีให้เซิร์ฟเวอร์ส่งข้อมูลมาทีละส่วนแบบต่อเนื่อง ใช้ทำให้คำตอบแชทค่อย ๆ พิมพ์ทีละคำ
Hallucination
อาการที่ AI สร้างข้อมูล/ตัวเลขที่ไม่มีอยู่จริงขึ้นมาเอง — ปัญหาหลักที่ RAG ถูกออกแบบมาเพื่อลด
เอกสารนี้สรุปอธิบายภาพรวมส่วนหลัก ของระบบ chatbot เพื่อให้เข้าใจการทำงานโดยรวม — ไม่ใช่การทำคู่มือการติดตั้งหรือใช้งานเชิงเทคนิค
