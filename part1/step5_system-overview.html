1.1

แนวคิดการทำงาน: RAG คืออะไร

ปัญหาของแชทบอท AI ทั่วไป (เช่น ChatGPT แบบเปล่า ๆ) คือมันตอบจาก "ความจำ" ที่เรียนรู้มาตอนฝึกโมเดล ซึ่งอาจไม่มีข้อมูลล่าสุด ไม่มีข้อมูลเฉพาะของหน่วยงาน และที่อันตรายที่สุดคือ สามารถ "มั่ว" ตัวเลขหรือข้อเท็จจริงขึ้นมาเองได้ (เรียกว่า hallucination) — ซึ่งยอมรับไม่ได้สำหรับข้อมูลราชการที่ต้องอ้างอิงได้

RAG (Retrieval-Augmented Generation) แก้ปัญหานี้ด้วยการ "บังคับ" ให้ AI ตอบจากเอกสารจริงเท่านั้น โดยแบ่งการทำงานเป็น 2 ขั้นเสมอ:

  1. Retrieval (ค้นหา) — เมื่อผู้ใช้ถามคำถาม ระบบจะค้นหาย่อหน้า/ส่วนของเอกสารที่เกี่ยวข้องที่สุดจากคลังเอกสารที่นำเข้าไว้ล่วงหน้า
  2. Generation (สร้างคำตอบ) — ส่งย่อหน้าที่ค้นเจอ (เรียกว่า "context") ให้โมเดลภาษา (LLM) อ่าน แล้วให้เรียบเรียงเป็นคำตอบภาษาธรรมชาติ พร้อมอ้างอิงแหล่งที่มา

ผลลัพธ์คือคำตอบที่ ตรวจสอบย้อนกลับได้ — ทุกคำตอบสามารถอ้างอิงกลับไปยังเอกสารต้นฉบับ ข้อ [1] [2] [3] ที่ระบบใช้ประกอบคำตอบ และถ้าไม่มีข้อมูลในเอกสาร ระบบจะบอกตรง ๆ ว่าไม่มีข้อมูล แทนที่จะเดา

1.2

สถาปัตยกรรมระบบโดยรวม

ระบบประกอบด้วย 5 ส่วนหลักที่ทำงานร่วมกัน — ผู้ใช้ไม่เห็นความซับซ้อนนี้ เห็นแค่หน้าแชท

หลักการออกแบบสำคัญ: ทุกส่วนเป็นบริการแยกกัน (loosely coupled) — ถ้า DeepSeek ล่ม ระบบยังค้นเอกสารได้ ถ้า API ภายนอกล่ม ระบบยัง fallback กลับไปตอบจากเอกสารอย่างเดียวได้ ไม่มีจุดใดจุดหนึ่งทำให้ทั้งระบบหยุดทำงาน (ยกเว้นฐานข้อมูลและ backend เอง)

🖥️ Frontend src-react/

React + TypeScript หน้าตาที่ผู้ใช้เห็น — แชท, แลนดิ้งเพจ, แดชบอร์ดแอดมิน, พอร์ทัลข้อมูล

⚙️ Backend app/

FastAPI จัดการตรรกะทั้งหมด: รับคำถาม ค้นเอกสาร เรียก LLM ยืนยันตัวตน บันทึก log

🗄️ ฐานข้อมูล PostgreSQL

เก็บทั้งข้อมูลทั่วไป (ผู้ใช้, ประวัติแชท) และเวกเตอร์ของเอกสาร (ผ่านส่วนขยาย pgvector) ในที่เดียว

🧠 โมเดลภาษา DeepSeek

รับผิดชอบ "เรียบเรียงคำตอบ" และ "ขยายคำค้นหา" เท่านั้น — ไม่ได้เป็นแหล่งความรู้โดยตรง

🔤 Embedding Ollama bge-m3

โมเดลรันในเครื่อง/เซิร์ฟเวอร์เอง แปลงข้อความไทยเป็นตัวเลข (เวกเตอร์) เพื่อเทียบความหมาย

📄 OCR Typhoon API

อ่านตัวอักษรจาก PDF ที่เป็นภาพสแกนภาษาไทย ใช้ตอนนำเข้าเอกสารเข้าคลังความรู้

1.3

ขั้นตอนการทำงานเมื่อผู้ใช้ถามคำถาม

นี่คือหัวใจของระบบ (app/services/rag.py, app/routers/chat.py) — คำถาม 1 ข้อ ผ่านกี่ขั้นตอนกว่าจะกลายเป็นคำตอบ

รายละเอียดแต่ละขั้นตอน (ไฟล์อ้างอิง):

  1. คัดกรองเจตนา (Intent Router) — app/services/intent_router.py. คำถามประเภททักทาย ขอบคุณ ขอข้อมูลส่วนบุคคล หรือหลุดหัวข้อ จะถูกตอบด้วยข้อความสำเร็จรูปทันที ไม่ต้องเสียเวลาค้นเอกสารหรือเรียก LLM คำถามเชิงขอคำแนะนำยังค้นเอกสารได้แต่ระบบจะเลี่ยงการ "สั่งยา/สั่งวิธีรักษา" ตรง ๆ
  2. เลือกหมวดสินค้า (Domain Router) — app/services/domain_router.py. ทำงานเฉพาะเมื่อผู้ใช้เลือกหมวด "ทั้งหมด" — LLM จะวิเคราะห์คำถามแล้วเดาว่าควรค้นเฉพาะหมวดไหน (เช่น กุ้ง, โคนม) เพื่อความแม่นยำ ถ้าเดาไม่ได้ก็ค้นทั้งหมดตามเดิม (ไม่แย่ไปกว่าการไม่ทำเลย)
  3. ขยายคำค้นหา (Query Expansion) — expand_query() ใน rag.py. คำถาม 1 ข้อ อาจมีหลายแง่มุม LLM จะช่วยแตกออกเป็น 2-3 คำค้นหาย่อยที่ครอบคลุมมุมต่าง ๆ (เช่น "อาการของโรค" + "วิธีป้องกัน")
  4. ค้นหาเวกเตอร์ (Vector Retrieval) — คำค้นหาแต่ละคำถูกแปลงเป็นเวกเตอร์ด้วย bge-m3 แล้วค้นใน PostgreSQL/pgvector ด้วย cosine similarity (ความคล้ายเชิงมุม) หาย่อหน้าที่ใกล้เคียงที่สุด 10 อันดับต่อคำค้นหาย่อย ทำงานคู่ขนานทุกคำค้นหาย่อยพร้อมกันเพื่อความเร็ว
  5. คัดกรอง + จัดอันดับใหม่ (Rerank) — rerank_chunks(). ตัดย่อหน้าที่คะแนนต่ำกว่า 0.35 ทิ้ง แล้วให้คะแนนพิเศษกับเอกสารที่ ใหม่กว่า และมาจากหน่วยงานทางการ (สศก., กรมปศุสัตว์ ฯลฯ) เพื่อไม่ให้เอกสารเก่าที่ OCR ไว้แย่งที่เอกสารทางการฉบับล่าสุด
  6. เสริมข้อมูลสด (Tool Routing) — app/services/tool_router.py. ก่อนตอบ DeepSeek จะพิจารณาว่าคำถามต้องใช้ "ข้อมูลสด" หรือไม่ (ราคาสินค้าล่าสุด, พยากรณ์อากาศ, ระดับน้ำ, ศัตรูพืชระบาด ฯลฯ) แล้วเลือกเรียก API ภายนอกที่เกี่ยวข้องแบบคู่ขนาน ผลลัพธ์ถูกผสมเข้ากับบริบทก่อนส่งให้ LLM ตอบ — ถ้าเรียกไม่สำเร็จ ระบบ fallback กลับไปใช้กติกาคำสำคัญแบบเดิม ไม่กระทบการตอบ
  7. สร้างคำตอบ (Answer Generation) — DeepSeek อ่านคำถาม + ประวัติการสนทนา + บริบทที่ค้นได้ทั้งหมด แล้วเรียบเรียงคำตอบพร้อมอ้างอิงหมายเลข [1][2][3] ตอบแบบสตรีมทีละคำ (คล้าย ChatGPT พิมพ์ทีละตัวอักษร) ผ่าน Server-Sent Events
  8. บันทึกและงานเบื้องหลัง — คำถาม/คำตอบถูกบันทึกลง qa_logs เพื่อใช้วิเคราะห์ในแดชบอร์ดแอดมิน ส่วนคำถามแนะนำต่อยอด (follow-up chips) จะถูกสร้างแบบ background หลังตอบเสร็จแล้ว เพื่อไม่ให้ผู้ใช้ต้องรอ
หลักการสำคัญ

ถ้าระบบค้นไม่เจอเอกสารที่เกี่ยวข้องเลย (coverage = "none") ระบบจะไม่ปล่อยให้ DeepSeek ตอบแบบเดา แต่จะตอบข้อความสำเร็จรูปว่าไม่มีข้อมูลในเอกสารทันที — นี่คือกลไกป้องกัน hallucination ที่สำคัญที่สุดของระบบ

1.4

ขั้นตอนการนำเข้าข้อมูลเข้าคลังความรู้ (Ingestion)

ก่อนแชทบอทจะตอบอะไรได้ ต้อง "ป้อน" เอกสารเข้าระบบก่อน — สคริปต์หลักคือ scripts/batch_ingest.py

  1. เตรียมโฟลเดอร์ PDF ไว้ที่ pdf/<หมวดสินค้า>/ พร้อมไฟล์ index.json ที่ระบุ หมวดหมู่ ปี หน่วยงานเจ้าของเอกสาร และ URL ต้นฉบับ
  2. ระบบส่งแต่ละหน้า PDF ไปให้ Typhoon OCR อ่านตัวอักษรภาษาไทยออกมาเป็นข้อความ (ทำเป็นชุด ๆ เพื่อเลี่ยงโดนจำกัดอัตราการเรียก API)
  3. ข้อความที่ OCR ได้ถูกแคชไว้ที่ data/ocr_output/ — ถ้าต้องรันซ้ำ ระบบจะข้ามขั้นตอน OCR ได้ (ประหยัดเวลา/ค่าใช้จ่าย)
  4. ตัดข้อความเป็นชิ้นย่อย (chunk) ขนาด ~1,500 ตัวอักษร ทับซ้อนกัน 200 ตัวอักษร (กันบริบทขาดตรงรอยตัด)
  5. แต่ละชิ้นถูกแปลงเป็นเวกเตอร์ด้วย Ollama bge-m3 แล้วบันทึกลงตาราง knowledge_base

มีสคริปต์ย่อยสำหรับสถานการณ์ต่าง ๆ:

  • scripts/ingest_missing.py — นำเข้าเฉพาะ PDF ใหม่ที่ยังไม่มีในระบบ (ไม่ต้องรันใหม่ทั้งหมด)
  • scripts/reingest_from_ocr.py — สร้าง embedding ใหม่จากข้อความ OCR ที่แคชไว้แล้ว (เช่น ตอนปรับขนาด chunk ใหม่)
  • scripts/ingest_oae_sheet.py — ดึงเอกสารจำนวนมากจาก Google Sheet ของสำนักงานเศรษฐกิจการเกษตร (OAE) แบบสตรีม ทีละไฟล์ ทำงานต่อได้แม้หยุดกลางคัน
1.5

ระบบผู้ใช้งานและสิทธิ์การเข้าถึง

👤 ผู้ใช้ทั่วไป (Guest)

เข้าใช้แชทได้ทันทีไม่ต้องสมัคร ระบุตัวตนด้วย UUID ชั่วคราว บทสนทนาเก็บแบบ sliding window (10 ข้อความล่าสุด)

🔐 ผู้ใช้ลงทะเบียน

สมัครด้วยอีเมล + รหัส OTP 6 หลัก (ส่งผ่าน SMTP) เข้าสู่ระบบด้วยอีเมล/รหัสผ่าน ยืนยันตัวตนด้วย JWT (หมดอายุ 8 ชม.) ประวัติแชทถูกบันทึกถาวร

🛡️ ผู้ดูแลระบบ (Admin)

ล็อกอินแยกต่างหาก จัดการคลังความรู้ ดูสถิติ วิเคราะห์คำถามที่ตอบไม่ได้ จัดการหมวดหมู่สินค้า

💬 LINE

ผู้ใช้ LINE ถามผ่าน Rich Menu ได้เช่นกัน ระบบยืนยันด้วยลายเซ็น HMAC ของ LINE แล้วใช้ RAG pipeline เดียวกับหน้าเว็บ

รหัสผ่านทุกบัญชีถูกแฮชด้วย PBKDF2 (ไม่เก็บรหัสผ่านจริง) การพิสูจน์ตัวตน API ใช้ JWT มาตรฐาน (HS256) ปุ่มล็อกอินผ่าน Google/Facebook/LINE ถูกถอดออกแล้ว เหลือเฉพาะอีเมล/รหัสผ่านเพื่อความง่ายในการดูแล

1.6

ระบบเสริมรอบข้าง

นอกจากแชทหลัก ระบบยังมีชั้นข้อมูลและหน้าจอเพิ่มเติมที่สร้างมูลค่าให้หน่วยงาน:

  • API สาธารณะ (/api/v1) — ให้หน่วยงาน/นักพัฒนาภายนอกดึงข้อมูลราคาสินค้า สถิติ และผลตอบคำถามผ่าน API มาตรฐาน มีระบบกุญแจ API และจำกัดอัตราการเรียก
  • พอร์ทัลข้อมูล (/portal) — หน้าแสดงราคาสินค้าสด ความลึกของคลังความรู้ และลิงก์ต่อไปยังแชทโดยตรง
  • แดชบอร์ดผู้บริหาร (/dashboard) — สรุปตัวชี้วัดตามมิติการตัดสินใจ (การผลิต/ตลาด/ความเสี่ยง/การเงิน/ฟาร์ม) แนวโน้ม 30 วัน และช่องว่างของข้อมูล
  • แบบสำรวจความพึงพอใจ (/survey) — เก็บความคิดเห็นผู้ใช้ แยกอัตโนมัติว่ามาจากเว็บหรือ LINE
  • เว็บผลการทดสอบ (Benchmarks) — เว็บไซต์แยกที่สรุปผลทดสอบคุณภาพคำตอบ (150 คำถามต่อหมวดสินค้า) เผยแพร่ที่ OAE-chatbot-benchmarks.netlify.app

ขั้นตอนการติดตั้งระบบตั้งแต่ต้นจนใช้งานได้

มี 2 วิธี — เลือกวิธี Docker ถ้าต้องการติดตั้งเร็วและรบกวนเครื่องน้อยที่สุด (แนะนำสำหรับ demo/ทดสอบ), เลือกวิธีติดตั้งเองถ้าต้องการพัฒนาโค้ดต่อ

วิธีที่ 1 — ใช้ Docker (ง่ายที่สุด)

  1. ติดตั้ง Docker Desktop
  2. คัดลอกไฟล์ .env.example เป็น .env แล้วกรอกค่าจริง (อย่างน้อย: DEEPSEEK_API_KEY, TYPHOON_API_KEY, JWT_SECRET, ADMIN_PASSWORD)
  3. รันคำสั่งเดียว:
docker compose up -d

คำสั่งนี้จะเริ่ม 3 บริการพร้อมกัน: แอปหลัก (FastAPI), PostgreSQL+pgvector, และ Ollama (พร้อมดึงโมเดล bge-m3 อัตโนมัติผ่านบริการ ollama-pull)

  1. นำเข้าเอกสารเข้าคลังความรู้ครั้งแรก (ต้องมี PDF อยู่ในโฟลเดอร์ pdf/ ก่อน):
docker compose run --rm batch-ingest
  1. เปิดเบราว์เซอร์ไปที่ http://localhost:8000

วิธีที่ 2 — ติดตั้งเองบนเครื่อง (สำหรับพัฒนาโค้ด)

ก) เตรียมเครื่องมือพื้นฐาน

  • Python ≥ 3.12 และ uv (ตัวจัดการแพ็กเกจ Python ที่โปรเจกต์นี้ใช้แทน pip)
  • Node.js 20+ และ npm (สำหรับ frontend)
  • PostgreSQL 16 พร้อมส่วนขยาย pgvector (หรือใช้ image pgvector/pgvector:pg16 ผ่าน Docker เฉพาะฐานข้อมูล)
  • Ollama ติดตั้งในเครื่อง แล้วดึงโมเดล embedding:
ollama pull bge-m3

ข) ติดตั้ง Backend

# ติดตั้งไลบรารีตาม pyproject.toml / uv.lock
uv sync

# สร้างไฟล์ .env จาก .env.example แล้วกรอกค่าจริง
cp .env.example .env

# รันเซิร์ฟเวอร์ (สร้างตารางในฐานข้อมูลอัตโนมัติตอนเริ่มทำงานครั้งแรก)
uv run rag_server.py    # http://localhost:8000

ค) ติดตั้ง Frontend

npm install
npm run build   # คอมไพล์ไปที่ dist/ — FastAPI เสิร์ฟไฟล์นี้โดยตรง
# หรือระหว่างพัฒนา ใช้โหมด hot-reload แทน:
npm run dev

ง) นำเข้าเอกสารเข้าคลังความรู้

4

Source Code เจาะลึก แยกตามส่วน

อธิบายไฟล์และฟังก์ชันสำคัญ ไล่ตามโฟลเดอร์ — คลิกเพื่อขยายรายละเอียดแต่ละส่วน

4.1 Backend — โฟลเดอร์ app/

Backend เขียนด้วย FastAPI แบ่งเป็น 4 ชั้นตามหน้าที่: routers (รับ request), services (ตรรกะทางธุรกิจ), db (คุยกับฐานข้อมูล), และไฟล์ระดับบนสุดสำหรับตั้งค่า/พิสูจน์ตัวตน/ประกอบแอป

app/main.py — จุดประกอบแอป (Application Factory)

สร้างอินสแตนซ์ FastAPI, ตั้งค่า CORS, mount โฟลเดอร์ static (frontend ที่ build แล้ว), และลงทะเบียนทุก router ในฟังก์ชัน lifespan() ที่ทำงานตอนเซิร์ฟเวอร์เริ่ม:

  • สร้าง connection pool ของฐานข้อมูลและตารางทั้งหมด (ถ้ายังไม่มี)
  • สร้างข้อมูลตั้งต้น (seed) เช่น หมวดสินค้าเริ่มต้น, บัญชีแอดมินคนแรกจากค่าใน .env
  • "อุ่นเครื่อง" โมเดล bge-m3 ผ่าน Ollama ให้พร้อมตอบก่อนรับ request แรก
app/config.py — ค่าคงที่และตัวแปรสภาพแวดล้อมทั้งหมด

อ่านค่าจาก .env ครั้งเดียวตอนเริ่มโปรแกรม เก็บ system prompt ของบอท (บุคลิก, กติกาการตอบ) และค่าปรับแต่งพฤติกรรม RAG ทั้งหมด เช่น:

  • TOP_K = 10 — จำนวนย่อหน้าที่ดึงมาต่อคำค้นหาย่อย
  • RETRIEVE_MIN_SCORE = 0.35 — คะแนนความคล้ายขั้นต่ำที่ยอมรับ
  • CHUNK_CHARS = 1500 — ขนาดชิ้นเอกสารตอนนำเข้า
  • สวิตช์เปิด/ปิดฟีเจอร์ต่าง ๆ เช่น DOMAIN_ROUTER_ENABLED, RAG_RERANK_ENABLED, LLM_TOOL_ROUTING_ENABLED
app/auth.py — การพิสูจน์ตัวตนและสิทธิ์

แฮชรหัสผ่านด้วย PBKDF2, ออก/ตรวจสอบ JWT, และมี dependency สำหรับ FastAPI สามแบบที่ router อื่นเรียกใช้: require_admin (ต้องเป็นแอดมิน), require_user (ต้องล็อกอิน), optional_user (ล็อกอินหรือไม่ก็ได้ — ใช้กับแชทที่รองรับทั้ง guest และสมาชิก)

app/models.py — รูปแบบข้อมูล Request/Response (Pydantic)

นิยามโครงสร้างข้อมูลทุกชนิดที่ API รับ-ส่ง เช่น ChatRequest, LoginRequest — FastAPI ใช้สิ่งนี้ตรวจสอบความถูกต้องของข้อมูลที่ส่งเข้ามาอัตโนมัติ และสร้างเอกสาร API ที่ /docs

app/db/ — ชั้นเข้าถึงฐานข้อมูล (psycopg2 + pgvector)
  • pool.py — จัดการ connection pool และคำสั่งสร้างตารางเริ่มต้น
  • users.py — ตาราง users, user_profiles
  • conversations.py — ประวัติแชท (guest sessions, ประวัติผู้ใช้, บทสนทนาแบบเต็ม)
  • knowledge_base.py — เพิ่ม/ค้น/ลบ ชิ้นเอกสารในคลังความรู้ (ฟังก์ชันค้นหาเวกเตอร์หลักอยู่ที่นี่)
  • price_facts.py — ราคาสินค้าเกษตรรายสัปดาห์ที่ซิงก์มาจาก NABC
  • qa_logs.py — บันทึกคำถาม-คำตอบ พร้อมจัดหมวดหมู่/จังหวัด/ฤดูกาลอัตโนมัติ
  • domains.py — ทะเบียนหมวดสินค้า/หมวดย่อยที่แอดมินสร้างเองได้
app/services/ — ตรรกะทางธุรกิจ (แกนหลักของระบบ)
  • rag.py — หัวใจของ RAG: ขยายคำค้นหา, ค้นหาเวกเตอร์, จัดอันดับใหม่ (อธิบายละเอียดในหัวข้อ 1.3)
  • clients.py — สร้าง client เชื่อมต่อ DeepSeek/Ollama แบบ singleton ใช้ซ้ำได้ทุก request (ไม่สร้างใหม่ทุกครั้ง — เร็วกว่าและประหยัดทรัพยากร)
  • embedding.py — เรียก Ollama แปลงข้อความเป็นเวกเตอร์
  • intent_router.py / domain_router.py — คัดกรองคำถามและเลือกหมวดสินค้า (หัวข้อ 1.3 ขั้นที่ 1-2)
  • tool_router.py — ให้ LLM เลือกเรียก API ภายนอกที่เกี่ยวข้องกับคำถาม (ราคา/อากาศ/น้ำ/ศัตรูพืช ฯลฯ)
  • web_search.py — ค้นหาเว็บเสริม (DuckDuckGo) เมื่อเอกสารในคลังไม่ครอบคลุม
  • ocr.py — ประมวลผล OCR สำหรับไฟล์ที่แอดมินอัปโหลดผ่านหน้าเว็บ
  • followups.py — สร้างคำถามแนะนำต่อยอด (chips) หลังตอบเสร็จ
  • nabc.py, doa_pest.py, ckan_enrich.py, api_catalog.py — ตัวเชื่อมต่อ API ข้อมูลเกษตรภายนอกแต่ละแหล่ง
app/routers/ — จุดรับ HTTP request (API endpoints)

เป็นแอป React เดียวที่มีหลายจุดเข้า (entry points) แยกกันตามหน้าที่ — คอมไพล์ด้วย Vite-plus แล้วนำไปวางที่ dist/ ให้ FastAPI เสิร์ฟตรง ๆ

4.5 การ Deploy สู่ Production

ระบบ production รันบน VPS (เซิร์ฟเวอร์เสมือน) แยกจากเครื่องพัฒนา — โค้ดต้นทางเก็บที่ GitHub (huack123/chatbot-OAE สาขา main เป็นตัวหลัก, มี GitLab เป็นสำเนาสำรอง) ขั้นตอนอัปเดตระบบจริงคือ: 

# บนเซิร์ฟเวอร์ /opt/chatbot-OAE
git pull
docker compose -f docker-compose.prod.yml up -d --build app

ห้ามแก้โค้ดตรงบนเซิร์ฟเวอร์จริง — ทุกการเปลี่ยนแปลงต้อง commit เข้า git แล้ว pull ลงมาเท่านั้น เพื่อให้โค้ดบน production กับใน repository ตรงกันเสมอ ค่าลับ (API keys, รหัสผ่าน) เก็บเฉพาะในไฟล์ .env บนเซิร์ฟเวอร์ (ไม่ commit เข้า git) ส่วน nginx ทำหน้าที่ reverse proxy รันอยู่บนโฮสต์จริง (ไม่ได้อยู่ใน container)

สิ่งที่ทีมพัฒนาต่อของหน่วยงานต้องรู้

ถ้าต้องส่งต่องานให้ทีม programmer ของหน่วยงานพัฒนาต่อ นี่คือจุดที่ควรอ่านก่อนแตะโค้ด

5.1 จุดที่ต้องระวังเป็นพิเศษ (Gotchas)

⚠️ Route handler ต้องเป็น def ธรรมดา

ฐานข้อมูลและ LLM client ในระบบนี้เป็นแบบ blocking (ไม่ async) ถ้าประกาศ endpoint เป็น async def โดยไม่มี await จริง จะทำให้ทั้งเซิร์ฟเวอร์ค้างระหว่างรอ request นั้น ใช้ def ธรรมดาเสมอ ยกเว้นมีการ await จริง ๆ (เช่น อ่านไฟล์อัปโหลด)

⚠️ ต้องปิด "thinking mode" ของ DeepSeek

โมเดล deepseek-v4-flash มีโหมดคิดแบบ chain-of-thought ที่ใช้โควตา token ร่วมกับคำตอบจริง เคยทำให้คำตอบว่างเปล่าประมาณ 10% ของครั้ง ระบบปิดโหมดนี้ไว้แล้วสำหรับทุกจุดที่ตอบผู้ใช้จริง — อย่าเปิดกลับโดยไม่เข้าใจผลกระทบ

⚠️ เทสต์เป็นสคริปต์ ไม่ใช่ pytest

รันทีละไฟล์ด้วย uv run tests/<ชื่อไฟล์>.py แต่ละไฟล์บันทึกผลเต็มไว้ที่ benchmarks/<ชื่อ>.md

⚠️ ต้องใช้ vp ไม่ใช่ Vite ตรง ๆ

โปรเจกต์ใช้ Vite-plus ผ่านคำสั่ง vp (เรียกผ่าน npm scripts เท่านั้น) ห้ามเรียก vite ตรง ๆ นอก npm scripts

5.2 ความปลอดภัยที่ควรแก้ไขก่อนส่งมอบใช้งานจริง

พบในโค้ดปัจจุบัน — ควรแก้ก่อนส่งมอบ

กุญแจ API ของ DeepSeek และ Typhoon OCR ถูกฝัง (hardcode) เป็นค่าสำรองไว้ในซอร์สโค้ดจริง ทั้งที่ app/config.py (บรรทัดตั้งค่า DEEPSEEK_API_KEY / TYPHOON_API_KEY) และ docker-compose.yml (รูปแบบ ${VAR:-sk-...}) ถึงแม้ไฟล์เหล่านี้จะไม่ใช่ .env จริง แต่เป็นไฟล์ที่ถูก commit เข้า git repository ซึ่งหมายความว่า:

1) ใครก็ตามที่เข้าถึง repository เห็นกุญแจนี้ได้ 2) ถ้าไม่ได้ตั้งค่า .env เอง ระบบจะใช้กุญแจนี้โดยอัตโนมัติโดยไม่รู้ตัว

ควรดำเนินการ: ขอกุญแจ API ชุดใหม่จากผู้ให้บริการ (DeepSeek, Typhoon), ลบค่าสำรองที่ฝังไว้ในทั้งสองไฟล์ออก (ให้ระบบ error ทันทีถ้าไม่ได้ตั้งค่า แทนที่จะทำงานเงียบ ๆ ด้วยกุญแจเก่า), และตรวจสอบว่ากุญแจเดิมยังถูกใช้อยู่ที่ไหนก่อนเพิกถอน

ข้อควรตรวจสอบเพิ่มเติมก่อนส่งมอบ:

  • เปลี่ยน ADMIN_PASSWORD จากค่าเริ่มต้น — ระบบจะแสดงคำเตือนใน log ถ้ายังใช้ค่า default
  • ตั้งค่า JWT_SECRET เป็นค่าสุ่มใหม่ อย่าใช้ค่า placeholder
  • ยืนยันว่าไฟล์ .env จริงไม่ถูก commit เข้า git (ตรวจสอบ .gitignore)
  • ทบทวนสิทธิ์การเข้าถึง GitHub/GitLab repository ว่าใครมีสิทธิ์เข้าถึงประวัติ commit เก่าที่อาจมีกุญแจฝังอยู่

5.3 ถ้าจะเพิ่มฟีเจอร์หรือปรับพฤติกรรมระบบ

  • เพิ่ม endpoint ใหม่ — สร้างฟังก์ชันในไฟล์ที่เหมาะสมใต้ app/routers/ ระบบจะเสิร์ฟให้อัตโนมัติ ไม่ต้องแก้ main.py
  • เพิ่มหมวดสินค้าใหม่ (เช่น สินค้าเกษตรชนิดใหม่) — สร้างผ่านหน้าแอดมิน (ทะเบียน kb_domains/kb_subdomains) ก่อน แล้วค่อยนำเข้าเอกสารด้วยสคริปต์ ingest โดยระบุหมวดที่สร้างไว้
  • ปรับพฤติกรรม RAG โดยไม่ต้องแก้โค้ด — ค่าคงที่ส่วนใหญ่ใน app/config.py อ่านจากตัวแปรสภาพแวดล้อม ปรับผ่าน .env ได้เลย เช่น เปิด/ปิด rerank, ปรับความยาวคำตอบ, ปรับ context budget
  • ก่อน commit ทุกครั้ง — รัน npm run build (ตรวจ type error) และอย่างน้อยหนึ่งใน uv run tests/test_chat*.py (ตรวจว่า RAG ยังตอบได้ปกติ)

ภาคผนวก: คำศัพท์เทคนิคที่ควรรู้

RAG (Retrieval-Augmented Generation)
เทคนิคให้ AI ตอบโดยอ้างอิงเอกสารจริงที่ค้นเจอ แทนที่จะตอบจากความจำล้วน ๆ
Embedding (เวกเตอร์)
การแปลงข้อความเป็นชุดตัวเลขที่แทนความหมาย ข้อความที่ความหมายใกล้กันจะมีเวกเตอร์ใกล้กัน
Cosine similarity
วิธีวัดความคล้ายระหว่างเวกเตอร์สองชุดโดยดูมุมระหว่างกัน ใช้หาเอกสารที่เกี่ยวข้องกับคำถาม
pgvector
ส่วนขยายของ PostgreSQL ที่เพิ่มความสามารถเก็บและค้นหาเวกเตอร์ได้ในตัว
LLM (Large Language Model)
โมเดลภาษาขนาดใหญ่ที่เรียบเรียงข้อความได้เป็นธรรมชาติ (เช่น DeepSeek, GPT, Claude)
Token
หน่วยย่อยของข้อความที่ LLM ใช้นับความยาวและคิดค่าใช้จ่าย (โดยประมาณ 1 token ≈ คำ/พยางค์สั้น ๆ)
Chunk (ชิ้นเอกสาร)
ส่วนย่อยของเอกสารที่ตัดมาเก็บแยกเป็นแถวในฐานข้อมูล เพื่อให้ค้นหาและอ้างอิงเฉพาะจุดได้
OCR (Optical Character Recognition)
เทคโนโลยีอ่านตัวอักษรจากภาพ/เอกสารสแกน แปลงเป็นข้อความที่คอมพิวเตอร์ประมวลผลได้
JWT (JSON Web Token)
โทเคนยืนยันตัวตนที่เข้ารหัสข้อมูลผู้ใช้ไว้ในตัวเอง ไม่ต้องเช็คฐานข้อมูลทุกครั้งที่ยืนยันสิทธิ์
SSE (Server-Sent Events)
วิธีให้เซิร์ฟเวอร์ส่งข้อมูลมาทีละส่วนแบบต่อเนื่อง ใช้ทำให้คำตอบแชทค่อย ๆ พิมพ์ทีละคำ
Hallucination
อาการที่ AI สร้างข้อมูล/ตัวเลขที่ไม่มีอยู่จริงขึ้นมาเอง — ปัญหาหลักที่ RAG ถูกออกแบบมาเพื่อลด
เอกสารนี้สรุปจากซอร์สโค้ดจริงของโปรเจกต์ (AGENTS.md, app/, db/init.sql, docker-compose.yml และไฟล์ตั้งค่าอื่น ๆ) ณ วันที่จัดทำ — หากมีการแก้ไขโค้ดในภายหลัง ควรตรวจทานเอกสารนี้ซ้ำให้ตรงกับระบบจริงก่อนนำไปอ้างอิงต่อ
